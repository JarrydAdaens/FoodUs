## Outcome and scope

Import a FoodUs-owned, versioned local library package additively as Products (Food in UI), Recipes and Meals. Preserve facts, reference quantities, incomplete records, ordered components, captured totals and relevant provenance without inventing metric weights, density, ingredients, links or yields. Imported definitions must be usable through search, viewing, editing and supported logging/loading. No diary records are supplied or imported.

The public repository contains generic format documentation, implementation and synthetic fixtures only. Account-specific adapters, originals, inventories, converted packages and private validation stay outside the checkout, including ignored folders. Do not read personal source values into context or logs. The private converter runs only after the implemented target contract is stable. No owner-phone import/reset, new scraping, accounts/network, cloud feature, grocery feature, density model, unit catalogue, percentage-to-mass engine or publication is authorized.

Keep one Story and one primary plan. The ordered steps below reflect dependencies and verification seams; they create no separate phase files or completion receipts. No commits, pull, push or tags. Preserve unrelated uncommitted work and the sealed prior delivery record.

## Selected contract

### Nutrition and quantities

Reuse all 43 `NutritionFacts` fields and `NutrientValue` semantics. Missing/null means unknown; numeric zero remains zero. Keep directly supplied energy rather than deriving it from macros. The wire contract documents each field's canonical unit explicitly, including energy, and accepts only that encoded unit. Optional percentage daily values live in bounded separate metadata and never become nutrient masses or calculation input. Keep relevant notes/provenance; do not retain an unbounded arbitrary source object.

Use a small shared reported-panel/reference value type, not a new unit catalogue: facts, declared basis, optional reference description and independently known metric amount. A description contains supplied positive amount where known, bounded unit/quantity text and raw descriptive text. Opaque text is never parsed as a conversion. Whole-item, reference-serving, unspecified and unavailable panel bases remain distinct. An unspecified panel is readable but cannot resolve portions.

Products gain explicit `METRIC_100` (legacy default) or `REFERENCE_SERVING` nutrition basis. In the latter, one selected Serving means the complete declared reference portion: for example, “1 serving (2 pieces)” contains the supplied panel, even when grams are unknown. Two servings scale it twice. Known grams/mL refer to that same reference and enable only compatible metric conversions. They are optional and cannot be inferred from package text or percentages. Preserve package/serving weights independently and validate that any claimed conversions agree with their declared scope. Apply the same basis to immutable Product snapshots. Existing values remain per 100 g/mL without rewriting numbers.

### Recipes and snapshots

Add explicit `DERIVED` and `REPORTED` Recipe nutrition modes. `DERIVED` keeps current linked ingredients, positive integer yield, strict completeness, compatible metric basis, graph validation and unpack semantics. `REPORTED` has an independent captured panel, genuinely nullable known integer yield, and ordered inline components (name, raw portion description, optional captured component facts, optional typed Product/Recipe link). Imported reported facts never come from an incomplete ingredient sum, and component facts never come from dividing the panel.

Reported links are provenance; they do not re-read mutable definition nutrition. Validate supplied links and cycles when accepting a package/save, but deletion of a linked definition must retain the inline description/facts, either setting the optional link null or retaining a non-resolving provenance identifier. Do not use the existing cascading ingredient relationship for these rows. Preserve order explicitly.

For reported whole-Recipe facts, Package fractions resolve even with unknown yield; Serving portions resolve only when a positive known yield is supplied. A declared per-reference Serving panel resolves its reference servings without needing a total yield. Converting that panel to a whole Recipe requires known yield and a compatible declared serving relationship. Metric conversion requires explicitly known compatible mass/volume for the same panel scope. Unspecified/unavailable bases remain visible and unloggable. Unsupported conversions show recoverable feedback and never manufacture a default yield of 1.

Make the Recipe and DiaryRecipe `servings` storage honestly nullable for reported mode through a data-preserving table rebuild, retaining required positive yield validation for derived mode. Add dedicated ordered reported-component rows for live definitions and captured snapshots, plus panel/mode/basis fields or owned companion rows. Keep legacy table names/IDs/columns, index/FTS/view behavior and foreign-key semantics. Choose the smallest Room mapping that passes the full migration fixtures before extending callers.

Add a new explicit reported snapshot discriminator (proposed calculation contract 2) carrying the panel, nullable yield, reference metadata and ordered inline components. Existing contracts 0 and 1 retain their exact readers/arithmetic, row values and copy behavior; only new reported captures use 2. Historical linked Recipe snapshots never acquire live catalogue links. New reported snapshots also store immutable component facts/text and opaque provenance only, with no foreign key to live catalogue rows; deleting or editing a live linked definition cannot erase snapshot provenance. Ordinary reported logging creates one captured Recipe diary entry. Reported Recipe unpack is unavailable in v1; show that unpack requires nutrition calculated from linked ingredients, and reject without writes. This avoids adding a new manual-component unpack feature that the recovered data does not require. Existing derived unpack behavior remains unchanged; never distribute a reported panel among components.

### Editing and Meal totals

Route reported Recipes to a mode-aware editor with Save/Cancel for panel, basis, nullable yield and inline rows. Do not pass them through the existing linked-only form and silently discard components. Names, notes and row reordering do not invalidate the captured panel. Adding/removing components, changing component amount/facts/link, yield, liquid status, or reference/basis metadata retains the previous reported panel as captured evidence and marks it “Needs review”. Logging from that panel remains unavailable until the user updates it or explicitly confirms it still applies to the displayed composition and basis. Never label reported facts as calculated. Do not add an automatic mode-conversion feature; ordinary derived editing remains unchanged.

Food editing exposes its actual reference basis, preserves unknown metric fields and retains panel/reference data on unrelated edits. A changed reference quantity cannot silently reinterpret the old panel: require explicit confirmation/update of the facts for that reference before Save. Default search/logging selects Serving for reference Foods and a supported portion for reported Recipes; unsupported metric controls are unavailable and show why.

Meal items retain absolute facts, position, known captured Measurement where supplied, raw portion text, descriptive quantities and bounded provenance. These descriptive fields never multiply facts. A separately reported Meal panel is stored/displayed beside the computed constituent sum and remains independent even when values disagree or constituents are incomplete. Loading always appends the individual absolute items; no balancing or replacement by the reported panel. Name/notes/reordering preserve panel applicability; item add/remove, amount scaling or nutrient changes mark it “Needs review” without altering captured facts. This flag does not block loading valid constituent snapshots, because loading uses those items, not the reported panel. Existing same-unit scale behavior scales an item's facts once and preserves the original raw description as provenance rather than relabeling it as a current amount. Carry descriptive provenance into ManualDiaryEntry and through copy/edit/restart so logging does not discard it.

### FoodUs local format and import transaction

Introduce `format: "foodus-library"`, integer `formatVersion: 1`, bounded opaque `namespace`, and `products`, `recipes`, `meals` arrays. Every record has nonempty bounded `externalId`, name and typed content. Identity is the tuple `(namespace, kind, externalId)`, not a concatenated ambiguous string or a numeric ID shared across kinds. References carry kind and externalId in this namespace. V1 permits derived Recipes only with fully linked typed measured ingredients and valid yield, and reported Recipes with the panel/components above. Meals contain ordered absolute snapshot items and optional provenance-only typed references. Do not reuse account field names or formats.

Publish one authoritative format description with synthetic examples alongside the importer and derive the private adapter from the implemented validator. Define enum values, missing/null rules, all nutrient units, basis/quantity relationships, order, metadata limits and reference rules. Reject unsupported versions, duplicate JSON keys/identities, unknown structural fields or encoded enums/units, invalid UTF-8, nonfinite/negative facts, nonpositive supplied amounts/yields, bad typed references and cycles. Permit documented bounded metadata fields only. Validation errors expose a record kind/index and stable generic code; never raw names/values, file contents, source URIs or throwable payloads.

Bound bytes before parsing, plus record count, total components, text lengths and graph depth. Initial v1 limits: 16 MiB UTF-8, 20,000 definitions total, 100,000 components/items total, 10,000 components/items per record and Recipe depth 64; namespace 128 characters, external ID 256, name 512, individual descriptive/note text 16,384, and metadata 65,536 UTF-8 bytes per record. Check limits while reading/parsing, including aggregate text bytes through the file cap. These conservative constants support a local personal library while bounding memory and graph work; validate sanitized private counts before converter delivery and document any required revision with boundary tests. No runtime tuning UI. A bounded in-memory validated import draft is sufficient; avoid copying the CSV path's unbounded read. Cancellation propagates and clears draft buffers.

Add a dedicated Room ledger with a unique namespace/kind/externalId tuple, canonical validated source-content digest and typed local target ID. It is not Product provider metadata. Canonicalization includes all retained semantic content and list order, normalizes object/map order and documented null/unknown equivalence, and does not hash raw JSON formatting. Identical imported content skips that record and preserves subsequent local edits. Any differing content for an existing identity rejects the complete package with a sanitized conflict; v1 has no overwrite resolution UI. A missing/deleted mapped target or inconsistent mapping also conflicts, rather than silently duplicating/rebinding. Fresh packages never name-match old CSV rows.

Preview is read-only: counts by kind, new/identical/conflicting records, unsupported portions and the legacy-flat overlap limitation. Confirm imports exactly the validated immutable draft. Inside one `TransactionProvider.withTransaction`, recheck ledger/dependency state, allocate/map IDs, write definitions/components/Meals/history and ledger, and validate the committed candidate graph. Reference existing mapped definitions only when present and semantically safe; a changed linked dependency for a derived import must reject rather than calculate unexpected facts from local edits. Reported provenance-only links can point to the mapped identity without taking its live values. No external references or forward dependency gaps are accepted. The transaction and coroutine cancellation prevent all partial writes; do not catch cancellation as success. Suppress double-submit. Settings, credentials, diary rows and old snapshots are outside the write set.
