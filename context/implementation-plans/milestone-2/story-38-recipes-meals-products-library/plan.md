## Outcome and scope

Provide one local personal library reached from **Settings → Recipes, Meals & Products**, immediately below **Daily goals**. Remove Home's top-bar Meals shortcut. Keep diary Save Meal, Load Meal and Story 39's bulk actions available.

The destination has Back, a title, name search, tabs ordered **Recipes / Meals / Products**, compact rows with explicit nutrition bases, and a full-width bottom action labelled **Create Recipe / Create Meal / Create Product**. Opening, creating or editing a definition requires no diary date or DiarySlot and never logs food. Loading a committed Meal remains a separate operation with an explicit day and DiarySlot.

Reuse existing repositories, typed identities, mode-aware editors and nutrition resolvers. Preserve local/imported definitions, captured quantities, reported panels, provenance, owned item IDs/order and historical DiaryEntry snapshots. Preserve the [Design domain and serving contracts](../../../design.md#domain-model-shared-vocabulary) and the delivered contracts in Stories [24](../story-24-meals-library-editor/plan.md), [26](../story-26-product-terminology-portions/plan.md), [27](../story-27-recipe-composition-portions/plan.md) and [28](../story-28-structured-personal-import/plan.md).

Exclude provider-catalogue management, OCR, relay, new sharing/accounts/network dependencies, photos, directions, sorting controls, bulk library operations, duplication, web import, a global terminology replacement and a new nutrition calculation system. Existing ingredient/product discovery remains available inside editors. No schema change is required. Planning and read/navigation work do not independently change the version; accepted Story closure follows the versioning policy.

Third-party studies, captures, account records and source-specific interpretations stay outside this checkout, including ignored folders. Public implementation fixtures and runtime evidence must use synthetic records. The owner phone was authorized for reference inspection; use a disposable emulator/test installation for mutation, failure, import and upgrade acceptance.

## Selected interaction and data contract

### Library state and local collection separation

1. Use a library-scoped ViewModel/state owner. Initial tab is Recipes. Retain one shared query across tabs and independent scroll position per tab while visiting editors, ingredient pickers and nested navigation. Use saved state/saveable list state for configuration restoration; ordinary process recreation restores navigation/tab/query/scroll where supported. Do not persist the search query to global preferences or logs.
2. Recipes lists all saved Recipe definitions, including derived and reported imports. Products lists only `ProductSource.Type.User` records, including personal imports. Provider rows remain excluded even when cached locally. Meals uses `MealRepository.observeAll()` and the same saved collection as diary Save/Load.
3. Add lightweight typed ID/name listing methods to the existing Product/Recipe repository boundaries, backed by Room queries. Select personal Products at the database boundary. No arbitrary first-page/record cap and no filtering after mixed Product/Recipe pagination. Preserve existing repository callers.
4. Filter names locally using trimmed, case-insensitive substring matching; blank/whitespace query shows the whole active collection. Use the same matching rule for all three tabs. Treat punctuation, apostrophes, `%`, `_` and numeric names literally; do not route a library query through barcode interpretation or raw FTS syntax. Proposed deterministic order is case-insensitive name, then stable typed ID; there is no new sort setting.
5. Keep lightweight identity/name results separate from row nutrition resolution. Resolve visible/prefetched Product/Recipe rows through existing repository/use-case observers and cancel subscriptions when no longer needed. Lazy rows use stable typed keys so equal numeric Product and Recipe IDs cannot collide. A missing/malformed/unresolvable definition remains an identifiable unavailable row with recoverable feedback, not a silently missing item or an empty collection. Avoid one unbounded recursive graph subscription per saved Recipe.
6. Model loading, populated, empty collection, query with no results and recoverable read error separately. Retrying refreshes the failed observation without clearing tab/query/scroll. Do not show no-results while still loading. Create remains reachable in ordinary empty/no-results states; write failures retain the draft for retry.

### Row layout and truthful nutrition

Use a reusable FoodUs row with a leading FoodUs fallback icon, name, explicit basis caption, carbohydrate/fat/protein values and trailing energy using `LocalEnergyFormatter` and units. No thumbnail storage/download feature is required. Content can wrap as font scale grows; avoid a rigid row height that clips name, basis or values. Decorative icons do not duplicate accessibility speech. Row selection has a meaningful accessible label and inspection identity.

| Definition | Primary row basis and source | Unavailable / reported behavior |
| --- | --- | --- |
| Metric Product | Stored canonical facts, labelled per 100 g or per 100 mL according to its declared basis | A missing serving weight does not prevent showing known per-100 facts; do not infer weight/density. |
| Reference-serving Product | Stored facts for its declared reference serving; show the supplied reference description/quantity | No conversion to 100 g/mL without a real compatible basis. Preserve missing quantity text honestly. |
| Derived Recipe | `nutritionFor(Measurement.Serving(1.0))`, labelled per serving | Ingredient completeness and compatible-basis rules stay in the existing resolver. Do not calculate serving macros from per-100 fields or invent a weight. |
| Reported Recipe | Existing reported resolver for one reference serving, labelled per serving with its declared reference when available | Whole-Recipe panel with unknown yield, unspecified basis or needs-review cannot promise per-serving facts. Show serving nutrition unavailable plus an explicit reason and retained reported-panel detail affordance; never divide by an invented yield or substitute whole-Recipe facts under a per-serving label. |
| Meal | Strict aggregate of saved constituent absolute facts, labelled whole saved Meal / saved bundle | If a reported panel exists, keep it separately labelled and inspectable. A compact secondary reported-panel marker/caption may lead to existing detail; it never replaces or silently repairs constituent totals. |

Preserve `NutrientValue` completeness: unknown is displayed as unknown, a true zero remains zero, and incomplete supplied values remain visibly incomplete. An unavailable calculated total is not a partial sum. Do not derive energy from macro arithmetic. Format localized units and nonfinite/overflow failures safely. Library projections are read only and never write recalculated facts into definitions or diary history.

### Create, edit, delete and load

- Add Settings-origin Product/Recipe create routes without date/slot parameters. Reuse existing create screens and supply a completion callback that pops to the existing library entry. Existing diary create/promote routes keep their current behavior. Reuse typed update routes, including captured/reference and reported modes. The library back-stack entry owns retained state during these journeys.
- Add a distinct unsaved Meal draft mode rather than pretending a persisted Meal ID exists. Reuse Meal constituent capture, quantity editing, validation and explicit Save/Cancel. A blank name, empty bundle or invalid item cannot save. The new definition-creation use case validates the draft and calls `MealRepository.save` atomically; it must not read a diary selection. No Meal or backing Product is written before Save. Guard repeat submissions; cancel/failed save preserves the prior collection and creates no partial rows. A successful save returns to the Meals tab without logging.
- Editing a row opens its appropriate existing detail/editor. Preserve rename, supported constituent/portion edits, reported-panel review rules, Save/Cancel and confirmed deletion where already supported. Do not add Product/Recipe deletion as speculative new scope if their existing management flow does not offer it. Deleted/stale rows get recoverable navigation rather than an indefinitely blank editor; existing Product/Recipe null-as-loading paths need bounded loading/not-found/error handling where the new library exposes them.
- Keep new and existing Meal drafts isolated from the stored collection. Retained item IDs/order, creation time, quantity context and independent reported panel/provenance survive edits under the delivered repository rules. Never recreate imported records to make editing easier.
- Load Meal is a deliberate action on a committed saved Meal. Open a destination chooser with day and DiarySlot explicitly selected before confirmation; Settings origin carries neither. Do not use a hidden Home date or a dummy slot. An empty day/slot selection cannot apply. No configured slots produces helpful recovery and no write. Cancel makes no changes; repeated confirmation cannot duplicate entries; stale/deleted targets and apply failures are recoverable. Keep existing one-entry-per-constituent transactional apply behavior.
- A creation save that does not match the retained query keeps the query and presents success feedback rather than silently clearing search. Returning from any editor preserves scroll where the stable anchor remains; after deletion clamp to the nearest valid position.

### Navigation, layout and inspection

The Settings row matches adjacent row styling and is available with an empty diary/library. Library Back returns to Settings. Remove the obsolete Home entry and update affected previews/tests/callbacks without touching unrelated diary menus. Keep the title/search/tabs coherent under narrow widths and larger text; use localized resources instead of hardcoded English in composables.

Place the creation action in a Scaffold bottom area with navigation/IME inset handling and corresponding list content padding. The last row must scroll fully above it. Back dismisses the keyboard or editor sub-flow in the established order before leaving the library. Inspect light/dark themes, focus order and enlarged text. Every new/changed Compose call site has source-oriented `uiName`/surface scope, and repeated row instances remain distinguishable through typed data identity without logging personal names.

## Questions and assumptions

- **Search and ordering:** proposal is one shared literal name-substring query, initial Recipes tab and deterministic name/ID order. Story 38 does not specify alternate sorting or fuzzy matching. These choices are ready to implement and do not require an added control.
- **Imported Recipe without a usable serving:** accepted data can have unknown yield or an unavailable/review-required panel. The per-serving row must remain unavailable with an explanation while full reported evidence remains accessible. This resolves the display requirement without inventing a serving.
- **Images:** no saved-image requirement exists in the current domain. Use FoodUs fallback icons for all rows; a photo storage/download feature is excluded.
- **Restoration:** retain library navigation state across editor visits and ordinary configuration recreation. Persisting unsaved drafts across process death is not added scope; abandoned drafts must never become definitions automatically. Document any process-restoration limitation found in existing navigation.
- **Scale/graphs:** lightweight name lists and visible-row observers avoid whole-library hydration, but an extreme single Recipe DAG remains an existing documented risk. Measure representative synthetic data before optimizing; report a reproducible acceptance blocker rather than silently hiding or truncating definitions.
- **Authorization boundary:** the owner authorized implementation on 2026-10-27 after the study and plan. Story 38 was accepted and closed on that date; no commit or publication was authorized.
